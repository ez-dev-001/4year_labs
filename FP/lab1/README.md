# Лабораторна робота №1 — варіант 4

Інформаційна система «Інформаційні сервіси мережі факультету» (Haskell + MySQL).

## Що всередині

- `schema.sql` — БД `faculty_services`, 6 таблиць і тестові дані:
  `service_types` (види), `authors` (автори), `services` (назва, автор, анотація, вид, версія,
  умови, кінцевий термін, правила), `users` (користувачі), `registrations` (дані реєстрації
  користувачів у сервісах), `usage_stats` (статистика використання).
- `Main.hs` — консольна програма. Клас `Table` (методи `tableName`, `columns`, `fromRow`, `toRow`)
  і 6 його екземплярів, по одному на таблицю. Перегляд, додавання, коригування й видалення працюють
  для будь-якого екземпляра класу. Є також пошук сервісу за словом і звіт зі статистики.

## Запуск (Windows)

1. Встановити MySQL (Server + Shell/Client) і GHC (через GHCup). Перевірити, що `mysql` і `ghc` є в PATH.
2. Створити БД: `mysql -u root -p < schema.sql` (увага: скрипт перестворює БД `faculty_services`, наявні в ній дані буде видалено)
3. У `Main.hs`, у `dbConn`, вказати свій пароль (`--password=...`).
4. Зібрати й запустити:
   ```
   chcp 65001
   ghc -outputdir build-main Main.hs -o lab1
   lab1
   ```
   `chcp 65001` потрібен, щоб кирилиця в консолі відображалась правильно.

Програма звертається до MySQL через консольний клієнт `mysql` (запит передається через stdin),
тому, крім GHC, нічого встановлювати не треба.

## Тести

`Test.hs` перевіряє чисті функції, роботу з MySQL і програму цілком (ввід через stdin).
Тести створюють окрему БД `faculty_services_test`, робочу `faculty_services` не чіпають.
Їм потрібен той самий логін/пароль, що в `dbConn`.

```
ghc -outputdir build-main Main.hs -o lab1
ghc -outputdir build-test -main-is Test Test.hs -o test
test
```

Рядки «Помилка MySQL» у виводі тестів очікувані: це перевірки, що погані дані відхиляються.

Що покрито (кожен пункт — знайдена й виправлена вразливість):

- SQL-ін'єкції, зокрема на сервері з режимом `NO_BACKSLASH_ESCAPES` (раніше значення поля
  могло виконати `DROP TABLE`); сесія тепер сама задає `sql_mode`.
- Нестрогий сервер більше не записує `0` і `0000-00-00` замість невірних чисел і дат.
- Перевірки в схемі: порожні назви, від'ємні хвилини, повторна реєстрація (CHECK, UNIQUE).
- Дані з табуляцією, переносом рядка, `\`, NUL, emoji зберігаються й читаються без змін
  (раніше перенос рядка в БД валив програму, а табуляція тихо ставала пробілом).
- Пошук: `%` і `_` шукаються як звичайні символи, а не як шаблони LIKE.
- Видалення/зміна неіснуючого id повідомляє «не знайдено», а не «готово».
- Програма не падає: кінець вводу (Ctrl+Z), невалідний UTF-8, переповнення числа,
  відсутній `mysql` у PATH, значення довше за ліміт командного рядка, CRLF у вводі.

Другий раунд (пошук ін'єкцій поза тестами):

- Вивід підроблявся: перенос рядка в назві малював у списку фейковий запис, ESC-послідовності
  (очищення екрана, запис у буфер обміну через OSC 52) і перемикачі напрямку тексту (U+202E)
  доходили до терміналу. Тепер дані з БД виводяться через `safe`: керуючі й невидимі символи
  показуються як `\x..`.
- Ін'єкція аргументу: значення `LAB1_DB="--init-command=DROP TABLE …"` ставало опцією `mysql`
  і виконувало SQL. Тепер ім'я БД передається як `--database=…`.
- Підміна програми (Windows): `mysql.exe`, підкладений поруч із програмою чи в поточний каталог,
  запустився б замість справжнього клієнта. Тепер клієнт шукається лише в абсолютних каталогах PATH.
- Назва з самих табуляцій, `\r`, нерозривних пробілів чи BOM проходила перевірку на порожнечу.
  Тепер назви й логіни мусять містити літеру чи цифру.
- Значення, що закінчується на `\r`, втрачало його при читанні (тепер так лише у Windows, де
  `\r` — частина переводу рядка).
- Фаззинг: 3000 випадкових склейок небезпечних фрагментів (лапки, `\`, коментарі, `\!`, `delimiter`,
  `system`, NUL, Ctrl+Z, emoji…) у звичайному режимі сервера й у `NO_BACKSLASH_ESCAPES` — жодної
  розбіжності, жодна команда клієнта `mysql` не виконалась. Скорочена версія (2×250) є в `Test.hs`.

CHECK-обмеження працюють у MySQL 8.0.16+ і MariaDB 10.2+.
